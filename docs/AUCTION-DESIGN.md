# BBK AUCTION — Design Pack

อัปเดต: 23 กันยายน 2026

## 1. ขอบเขตที่ยืนยันแล้ว

- สร้างระบบใหม่ทั้งหมด ไม่แก้ ไม่ย้ายโค้ด และไม่ย้ายข้อมูลจากระบบเดิม
- ใช้ Next.js + Vercel + Supabase (Postgres, Auth, Storage, Realtime)
- ทุกพอร์ทัลใช้ฐานข้อมูลกลางชุดเดียวกัน
- แยกประสบการณ์ใช้งานเป็น 3 พอร์ทัล: ลูกค้า (`/`), ผู้ขาย (`/seller`) และแอดมิน (`/admin`)
- ราคาประมูลและผู้ชนะตัดสินที่ฐานข้อมูลด้วย Postgres function แบบ atomic เท่านั้น
- Realtime ส่งจากข้อมูลที่ commit แล้ว ไม่ใช้สถานะในเบราว์เซอร์เป็นแหล่งความจริง
- ระบบเงินจริงและการแนบสลิปยังปิดไว้จนกว่าจะมีบัญชี/QR ร้านและค่าจัดส่ง
- โหมดเปิดตัวใช้ BBK เป็นผู้ขายรายเดียว สมาชิกทั่วไปเป็นผู้ประมูล และปิดรับสมัครผู้ขายภายนอก (อนุมัติโดยคุณตาล 23 กันยายน 2569)
- รายการที่แอดมินอนุมัติจะเปลี่ยนจาก `scheduled` เป็น `live` และจาก `live` เป็น `ended` ตามเวลาฐานข้อมูลอัตโนมัติ โดย Cron ตรวจทุกนาทีและหน้าเว็บมีเส้นทางตรวจซ้ำ
- ตอนปิด ระบบบันทึก `auction_results` และสร้าง Order เพียงหนึ่งรายการ พร้อมเลขคำสั่งซื้อ กำหนดชำระ 24 ชั่วโมง และ Audit event
- ผู้ประมูลใช้การยืนยันอีเมลของ Supabase และการอนุมัติโดยแอดมิน ไม่มี SMS หรือ Twilio (อนุมัติโดยคุณตาล 23 กันยายน 2569)
- ค่าธรรมเนียมผู้ซื้อ 10% และ VAT 7% ของค่าธรรมเนียม รวม 10.7% ของราคาชนะ ไม่รวมค่าส่ง
- ขั้นเพิ่มราคาใช้ราคาปัจจุบันเป็นเกณฑ์: ต่ำกว่า 1,000 บาท +10, 1,000–4,999 บาท +50, ตั้งแต่ 5,000 บาท +100
- กรณีไม่ชำระ: ครั้งแรกยกเลิกและเตือน ครั้งที่สองระงับรอแอดมินตรวจ; การบังคับใช้อัตโนมัติจะเปิดพร้อมระบบรับชำระ

## 2. สมมติฐานสำหรับต้นแบบ

- เข้าสู่ระบบด้วยอีเมลผ่าน Supabase Auth
- สมาชิกใหม่ได้รับสิทธิ์ `bidder` และต้องยืนยันอีเมล ส่งคำขอตรวจ และได้รับการอนุมัติจากแอดมินก่อนวางประมูล
- บัญชีผู้ขายจำกัดเฉพาะบัญชีหลักของ BBK จนกว่าจะมีการอนุมัติให้เปิด Marketplace
- ผู้ขายวางประมูลรายการของตนเองไม่ได้
- เงินเก็บเป็นหน่วยสตางค์ (`bigint`) เพื่อหลีกเลี่ยงค่าทศนิยมคลาดเคลื่อน
- เวลาในระบบใช้ `timestamptz` และเวลาของเซิร์ฟเวอร์เป็นเกณฑ์
- การต่อเวลาท้ายประมูลรองรับใน schema แต่ค่าเริ่มต้นเป็น 0 จนกว่าจะกำหนดกติกา

## 3. การตัดสินใจที่เจ้าของระบบยังต้องกำหนด

1. บัญชี/QR ทางการของร้าน ค่าจัดส่ง และเงื่อนไขคืนเงิน
2. ระดับ KYC และวงเงินที่ต้องตรวจเพิ่ม
3. reserve price, buy now, proxy bid และการยกเลิก bid
4. ช่วงเวลาและระยะเวลาต่อท้ายประมูล (anti-sniping)
5. การเสนอสิทธิ์ให้ผู้ประมูลอันดับถัดไปเมื่อผู้ชนะไม่ชำระ
6. การขนส่ง ประกัน ข้อพิพาท และการรับประกันความแท้

## 4. สถานะหลัก

### รายการประมูล

`draft → pending_review → scheduled → live → ended → settled`

เส้นทางพิเศษ: `rejected`, `cancelled`, `voided`

### ผู้ขาย

`pending → approved` หรือ `rejected / suspended`

### คำสั่งซื้อ

`pending_payment → paid → preparing → shipped → delivered → completed`

เส้นทางพิเศษ: `cancelled`, `disputed`, `refunded`

## 6. เส้นทางใช้งานและกรณีผิดพลาด

### ผู้ประมูล

ค้นหารายการ → ตรวจข้อมูล/ภาพ/เงื่อนไข → เข้าสู่ระบบ → ยืนยันอีเมล → ส่งคำขอตรวจ → แอดมินอนุมัติ → วาง bid → RPC ยืนยันหรือปฏิเสธ → ติดตามราคาจากฐานข้อมูล → ชนะหรือแพ้

- ปฏิเสธเมื่อบัญชีไม่พร้อม, bid ต่ำ, คำขอซ้ำผิดข้อมูล, เป็นเจ้าของรายการ, รายการไม่ live หรือเลยเส้นตาย
- Realtime หลุดแล้วต้องโหลดข้อมูลจริงใหม่ ไม่ใช้ราคาค้างในหน้าจอตัดสินผล

### ผู้ขาย

ทีม BBK เข้าสู่ระบบ → สร้าง draft → อัปโหลดหลักฐาน → ส่งตรวจ → แก้เมื่อถูกปฏิเสธหรือรอเปิดประมูล → ติดตามผล

- ผู้ขายแก้รายการของผู้อื่นไม่ได้ และแก้ราคาหัวประมูลโดยตรงไม่ได้
- ขั้นตอนจัดส่ง ข้อพิพาท และ payout ยังไม่เปิดจนกติกาได้รับอนุมัติ

### แอดมิน

เข้าสู่ระบบ → ตรวจบทบาทจากฐานข้อมูล → เปิดคิว → ตรวจหลักฐาน → บันทึกเหตุผล → อนุมัติ/ปฏิเสธ → เก็บ Audit event

- การเพิ่มแอดมิน, void ประมูล และงานการเงินต้องใช้สิทธิ์แยกและมีเหตุผล
- ห้ามลบประวัติ bid เพื่อแก้ปัญหา ให้ใช้สถานะ void/correction พร้อม audit

## 7. สถาปัตยกรรม

```text
Customer UI ─┐
Seller UI   ─┼─ Next.js/Vercel ─ Supabase Auth + Postgres + Storage
Admin UI    ─┘                         │
                                         └─ DB trigger → private Realtime Broadcast
```

- Frontend เรียก `place_bid(...)` RPC; ไม่มีสิทธิ์ insert ตาราง `bids` โดยตรง
- RPC ล็อกรายการประมูล ตรวจสิทธิ์/เวลา/ราคา/คำขอซ้ำ แล้วบันทึก bid และราคาปัจจุบันใน transaction เดียว
- Supabase Auth เป็นแหล่งความจริงของสถานะยืนยันอีเมล และฐานข้อมูลตรวจสถานะซ้ำก่อนรับคำขอและก่อนรับ bid
- ตาราง `bidder_verifications` เก็บสถานะคำขอและผลการตรวจของแอดมิน โดยเจ้าของบัญชีและแอดมินเท่านั้นที่อ่านได้ ชื่อเดิมคงไว้เพื่อให้ migration เดิมทำงานต่อเนื่อง
- RLS เป็นขอบเขตความปลอดภัยหลัก ทุก Route Handler หรือ Server Action ต้องตรวจสิทธิ์ซ้ำใกล้แหล่งข้อมูล
- การเชื่อม Realtime ใช้ห้อง `auction:<auction_id>` แบบ private
- งานดูแลระบบต้องเขียน audit event

## 8. เกณฑ์ผ่านระยะ Foundation

- เปิดทั้ง 3 พอร์ทัลได้และเห็นขอบเขตหน้าที่ต่างกันชัดเจน
- migration สร้าง schema, indexes, RLS, triggers และ `place_bid` RPC ได้จากฐานข้อมูลว่าง
- ไม่มี secret อยู่ใน repository และ build ได้แม้ยังไม่ต่อ Supabase
- ไม่มีปุ่มหรือเส้นทางที่ทำธุรกรรมเงินจริง
- lint และ production build ผ่าน
- ผู้ที่ยังไม่ยืนยันอีเมลหรือยังไม่ได้รับอนุมัติจากแอดมินต้องวาง bid ไม่ได้ทั้งจากหน้าเว็บและ RPC

## 9. เกณฑ์ผ่านก่อนเปิดใช้งานจริง

- ทดสอบ bid พร้อมกัน, bid ซ้ำ, bid หลังปิด, bid ต่ำกว่าขั้นต่ำ และ self-bid
- ทดสอบ RLS ทุกบทบาท รวมถึงผู้ไม่เข้าสู่ระบบ
- ทดสอบ Realtime reconnect และตรวจว่าหน้าจอ reconcile กับข้อมูลฐานข้อมูล
- ทดสอบปิดประมูลและสร้างผู้ชนะแบบ idempotent
- มีระบบสำรองข้อมูล, monitoring, audit log และคู่มือ incident response
- เจ้าของระบบอนุมัติกติกาธุรกิจและขั้นตอนเงินจริงทุกข้อ
